### L2-01 — High: full authority must be checked at each dispatch

**Issue/evidence.** Original §4:106–112 checks cancellation/parent/deadline in step 2 and at release, but compound operations repeat only steps 3–6. Step 4 names identity and policy, not the complete live cancellation, lock/session, deadline, sleep/TCC and controller state. A slow signature query or AX focus may finish after kill/deadline, then a second primitive may execute before release rejects its result. The existing test plan mentions cancellation before each primitive, but the normative sequence does not define its ordering. Current daemon executes a whole request via `DispatchQueue.main.sync` (`main.swift:4242`); AX messaging can block (`2202`). Merely queuing kill behind that execution does not implement the consumer's dispatch gate.

**Required fix.** Recheck complete authority and mark dispatch under a short coordinator barrier before every primitive, after slow validation. Serialize this with revocation; revoke-first permits no subsequent primitive, dispatch-first honestly reports possible effects and prevents later primitives. Slow OS calls cannot hold the mutex needed to cancel. Use a live authenticated controller lifeline to the actual executor, not daemon ancestry or relay exit. C request EOF is normal (`xyzlcu.c:161–162`); stopping that client does not establish daemon quiescence. Unknown cleanup keeps rearming unavailable. Added in §4, with explicit acknowledgment and per-primitive negative tests in §11.1. This does not claim the OS call can be recalled after dispatch.

### L2-02 — High: helper and hosted security surfaces need verified attribution

**Issue/evidence.** Original §7.1:439–441 promises protected variants/helpers, but matches bundle/team/signing aliases; §7.2:484,504–511 defines only flat overlay rules. It does not define how a different-ID XPC/login helper, Settings extension or shared security host inherits protection. A window owner outside the seed list can be a helper or host of a protected product. Consumer §2 requires exclusion of all Studio instances/helpers and forbids security/administration interfaces, including hosted subinterfaces. Current `BGTarget` describes one PID/window (`main.swift:2132`), and `bgTarget` constructs an AX application for that PID (`2202–2205`); there is no family-policy resolver here.

**Required fix.** Evaluate the verified actual owner, enclosing signed bundle, relevant nested helper/extension and hosting application graph. Authenticate package membership/OS host relationships; PPID, path containment, same Team ID or app-reported metadata alone cannot establish it. Protected ancestry/hosted content dominates an ordinary owner identity; unresolved attribution is Unknown and unavailable in Studio. Renaming a bundle must not erase its signed identity. System Settings extensions/shared hosts and password-manager/bank/admin/devtools content inside browsers, web views or Electron require reviewed surface support. An arbitrary repackaged clone cannot be universally identified; Unknown denial is necessary. Owner overlay rules can add denials but cannot invent trusted host edges. Bind provider/version/graph to policy and surface evidence. Added in §§6/7.1; unsupported providers keep the route unavailable.

### L2-03 — Medium: metadata discovery is not thumbnail permission

**Issue/evidence.** Original §4:108 and §7.1:464 already require protection and Unknown surface denial, including thumbnails in principle. However, §8.2:536–540 introduces an owner discovery exception without expressly making Allowed current-surface evidence a prerequisite for each candidate's thumbnail. This is an ambiguity, **not** evidence that L1 intentionally allowed protected thumbnails. Also, §8.1 freezes the main filter/shadow/contentRect but does not specify included child/composited surface attribution or how an Allowed classification stays valid through capture. A browser may retain its window identity while changing to a password manager or authentication sheet.

**Required fix.** Limit the exception to bounded metadata/icons; no capture/AX content may be used to bootstrap its own permission. Require reviewed Allowed app/window/current-composition evidence and continuity for each thumbnail/read/action; endpoint classifications alone cannot certify the interval. Freeze graph/composition/context and invalidate on change. Set `includeChildWindows=false` where supported, but do not treat it as embedded-content classification; refuse unsupported composition on older systems. The design adds `surface-continuity` and required attribution/composition/token fields in `SurfaceEvidence`, without claiming generic support. See §§6/8.1/8.2.

**SCK distinction.** Apple identifies [`SCWindow.windowID`](https://developer.apple.com/documentation/screencapturekit/scwindow/windowid) as the CG identifier; equality is not an incarnation proof. Current code selects `.first(windowID == wid)` (`main.swift:1650–1652,1823`), with no SC owner cross-check there. Revised §3.2 requires unique CG/SC matches, complete owner/process validation and use of the **same validated SCWindow object** in the filter. Fresh enumeration/filtering and same-process ABA refusal were already in L1. Apple publishes [`includeChildWindows`](https://developer.apple.com/documentation/screencapturekit/scstreamconfiguration/includechildwindows) for macOS 14.2+; stronger composition refusal is this design's requirement, not an Apple guarantee of content safety.

### L2-04 — High: `--allow-global` cannot waive protected-recipient enforcement

**Issue/evidence.** Original §10:617 preserves the standalone global/foreground policy while §10:620 requires protection on every entry point. Its explicit broad-route refusal at :621 covers reads only. Current `globalInputRefusal` returns no refusal for `allow:true,target:nil` (`main.swift:541–546`); `guardGlobalInput` samples frontmost immediately before returning (`548–578`). Focus can still change before an irreversible event, and pointer routing need not follow the sampled frontmost window. MCP batch can inject the opt-in (`4396`), so a proof-only guard does not fulfill universal policy.

**Required fix.** Any legacy write must prove permitted recipient/effect scope throughout dispatch. Generic global HID, pointer coordinates, PID-event hints, shared pasteboard and ambiguous `open -a` cannot inherit permission from opt-in or a frontmost snapshot. Refuse routes lacking the required guarantee, including every event in replay/batches and aliases. Postchecks do not repair input delivered to a protected target. Preserve flag syntax only where the resulting operation satisfies policy, and document the intentional compatibility break. Consumer global flags remain structurally forbidden. Added in §10, with focus/pointer/modal/sequence races in §11.1.

### L2-05 — Medium: authenticate the daemon before handing it the proof key

**Issue/evidence.** Original §5.1:144–150 correctly says same UID is insufficient, requires executor pinning and identifies FD forwarding. It does not prescribe the authentication/credential-delivery order or endpoint-bound handshake. A server that receives a session key can produce a correct HMAC over invented `Proof.executor` fields; that MAC cannot prove that the server was the pinned daemon. The C client connects to a path and sends argv without verifying executor code (`xyzlcu.c:74–80,120–133`); server admission checks UID only (`main.swift:4236–4238`). The existing `peerPid` helper (`4048–4050`) alone is not dynamic code/process-instance validation.

**Required fix.** Independently authenticate the actual connected peer's OS-bound instance and verified code/build identity before key FD or sensitive envelope transfer. Independently authenticate controller role; a profile/owner string cannot grant it. Bind fresh connection challenge, both endpoint identities and negotiated protocol/profile/integrity/policy into a verified handshake. Bracket PID-based lookups with exact start checks; reconnect/restart invalidates admission. A relay must not become an alternate proof producer. Unknown mechanism means consumer daemon unavailable; direct launch inherits an initially empty private channel, verifies the actual executed core and only then delivers secrets. The environment-key alternative is diagnostic-only, forbidden in Studio. Added in §§5.1/6.2. This protects the stated trusted-component/misrouting boundary, not an arbitrary same-UID attacker able to steal all credentials or replace trusted code/state.

### L2-06 — Medium: consuming an execution nonce is not consuming a response

**Issue/evidence.** Original §6:349 provides a bounded consumed-nonce ledger and strict sequence, and §4:120 requires the host to verify proof nonce/digests. Those stop duplicate dispatch, but do not explicitly require an atomic once-only transition when two valid copies of the same proof reach host publication. A repeated valid MAC can match the same request and create duplicate tool records or feed an old observation back into the model if no live pending/terminal state is checked. There is no current proof implementation to demonstrate this attack against.

**Required fix.** The consumer creates pending state before submission, binding full session/executor/nonce/sequence/request identity. Validate and consume it atomically with revocation/publication, across all output sinks. Completed/discarded/unknown/no-pending responses cannot publish or cause another operation. Keep bounded terminal state until expiry; refuse new work on capacity exhaustion, and never restore pending authority from chat/proof logs. Executor and host ledgers serve distinct purposes. Added in §4; duplicate valid-proof races and old-session/log replay enter §11.1.

### L2-07 — Medium: disappearance/rollback must not drop accepted owner rules

**Issue/evidence.** Original §7.2:470 treats absent optional overlay as built-ins only, while :484 makes owner additions protective. The proposed file has a revision, but no durable minimum/digest or distinction between first-use absence and deletion of an accepted overlay. A restored older file, missing file after an interrupted update or a restarted fresh daemon can silently drop additions. Original mode/no-follow/atomic-write checks already address ordinary file substitution hazards; they do not supply policy history. The current `lock.json` loader (`main.swift:2095–2101`) is legacy state, not a protected-policy implementation.

**Required fix.** Persist accepted/required overlay state and latest revision/digest in trusted owner continuity state. Refuse disappearance, rollback, same-revision altered content, missing continuity state and unreconciled partial updates. An explicit owner reset writes a new higher-revision empty overlay and revokes sessions; deletion is not reset. Bind expected policy to each new daemon/direct session and operation. Use verified directory-relative opens, descriptor identity and exactly one file link. Keep the same-UID limitation explicit: rewriting both policy and trusted state is outside this local file scheme's isolation claim. Added in §7.2 with recovery/rollback tests in §11.1.

### L2-08 — Medium: signature-valid does not establish safe no-prompt launch state

**Issue/evidence.** Original §9:599–602 rejects translocation and validates signature/path, and sets `promptsUserIfNeeded=false`. It does not specify quarantine/provenance handling, system-policy rejection/first-launch approval, or prohibited attempts to recover. A future implementation might clear quarantine or fall back to a different launch route to make an approved app work. Apple's [TN2206](https://developer.apple.com/library/archive/technotes/tn2206/_index.html) explains that subsystem trust policy is separate from code-signature validity. Current legacy `open` invokes `/usr/bin/open -a` (`main.swift:3621–3627`); it is explicitly unsuitable as the new typed dispatcher.

**Required fix.** Review and release-gate an OS-specific current system-trust provider, checking exact app eligibility at owner admission and before no-prompt submit. Unknown, blocked, approval-needed, changed or translocated state refuses. Never clear/modify quarantine or provenance, override system trust, approve first launch or retry through shell/URL/another launcher. No quarantine attribute is not evidence of trust. Owner installation/first launch happens separately and requires fresh allowlist admission/approval afterward. If no supported no-prompt trust mechanism satisfies the contract, launch stays unavailable. Added in §9 and error taxonomy; tests assert zero launch/modification calls on precheck failure. A signature/no-argument call also cannot prevent the app's own document restoration or behavior.

### L2-09 — Medium: stop forbidden capture acquisition, not just proof-cache reads

**Issue/evidence.** Original §8.1:528 forbids proof reuse of old frames and prewarm, but does not define admission cleanup or coexistence with legacy producers in the same resident executor. Existing streams retain images (`main.swift:1709`); `prewarmMainDisplay` opens display streams (`1848–1855`); diff processing retains prior pixels (`1994–2022`). Selecting a new guarded route does not stop old streams from acquiring protected pixels or late callbacks from repopulating buffers.

**Required fix.** Prefer a dedicated consumer executor with no legacy capture producers. Reuse requires a synchronous quiescence/purge barrier before admission; no legacy traffic may restart producers. Bind callbacks to generation; stop affected producers and invalidate retained content on policy/session changes. Cleanup uncertainty blocks admission. Every v0.8 producer, including legacy background acquisition, must maintain protected-surface exclusion; filtering output alone is insufficient. Added in §8.1; active-prewarm admission, late-callback and concurrent-legacy tests enter §11.1.

## Verification and disposition

Performed static source/design cross-checks, three independent read-only scoped agent reviews, selected Apple primary-source checks, and document consistency/embedded-JSON/local-link/whitespace validation. The design's original input was preserved for a local before/after diff; no source was changed. The implementation test matrix in revised §11.1 is **planned**, not executed by this review.

No build, fixture GUI, Screen Recording/Accessibility access, screenshot, input, launch, process-reuse experiment, signing acceptance, account action or publication was performed. No commit was created. All findings are **design addressed / implementation pending**. Machine schemas, handshake/evidence formats, provider code, supervision and real-Mac tests remain release work. In particular, generic window/AX/surface continuity and exact AppKit launch remain unavailable wherever they cannot meet the consumer's required guarantee. Neither this review nor a v0.8 version string enables XYZStudio tools.
